La concurrencia es un concepto que ya he manejado anteriormente en clases de programación y sistemas operativos, básicamente es cuando separamos las partes de un programa para que ejecuten en cualquier orden que no sea simplemente secuencial, típicamente al mismo tiempo (por ende el nombre concurrencia) y sin que afecte el resultado final.
Es bastante común hoy en día que las operaciones de un programa se lleven a cabo a través de múltiples procesadores unidos a la vez o en procesadores separados mediante hilos de ejecución (que son los threads que tratamos aquí).
Es muy útil porque muchos programas modernos manejan mucha información o procesos muy costosos y tardados así que programar con hilos en mente ayuda a reducir las cargas y tiempos de espera porque en lugar de quedarse congelado un programa, al separar sus procesos en hilos y manejarlos concurrentemente se puede hacer más rápido ocupando más poder computacional en lugar de enfocar una parte de él en toda una tarea.

En Java hace mucho se hacía simplemente con un "new Thread()" o implementando manualmente Runnable pero eso resultaba ser bastante costoso para la memoria y el CPU porque cuesta bastante arrancar y destruir hilos a cada rato.
Este problema fue resuelto en Java 5 con el framework de interfaz ExecutorService que crea un pool de threads reciclables, el programador le da un grupo de tareas y esta intefaz la reparte entre los hilos que no estén siendo usados, y si todos están ocupados pues las tareas se van a una cola.
Simplemente se envían objetos Runnable o Callable a la interfaz ExecutorService y la interfaz maneja su ciclo de vida y sus recursos.

Sin embargo, surge un problema cuando dos hilos (o hasta más) le quieren hacer un cambio a un mismo dato al mismo tiempo, si no mal recuerdo se llama "race condition" o condición de carrera.
Básicamente lo que pasa en estas situaciones es que ambos hilos le intentan hacer un cambio a un mismo dato, y ambos guardan el mismo (o diferentes) datos a la vez y uno termina sobreescribiendo al otro y se pierde información.
Hay algunas soluciones. Por ejemplo se puede usar el keyword synchronized para que solamente un hilo pueda modificar algún bloque o método protegido de código, o se pueden usar variables atómicas como AtomicInteger en lugar de primitivas cuyas operaciones se realizan en un solo paso que los otros hilos no pueden ver como "en proceso" solo sin hacer o terminado así que no se puede interrumpir, o se pueden usar colecciones concurrentes si los hilos comparten listas o hashmaps. Se pueden usar ConcurrentHashMap o CopyOnWriteArrayList que previenen concurrent write exceptions porque manejan su propia sincronización interna.

el NIO de Java (que significa New Input/Output) es una alternativa comparativamente más moderna a java.io que fue diseñada en 2002 para que el I/O fuera hecho más rápidamente y eficientemente al usar channels y buffers en lugar de data flows regulares.
La clase java.nio.file.Files trae consigo métodos estáticos para poder manipular archivos y directorios usando paths. Esta es aún más moderna, pertenece a NIO.2 y funciona junto a la interfaz java.nio.file.Path. Fue agregada junto con todo lo demás de NIO.2 en 2011 en Java 7.
Java 7 también trajo consigo mismo el bloque try-with-resources que garantiza que cualquier archivo que esté siendo manejado (con java.nio.file.Files) se cierre de forma automática cuando se termine lo cual evita bloqueos y memory leaks aun si hay un error.

Y la serialización se puede usar para guardar y recuperar objetos de una manera muy padre, si se implementa la interfaz Serializable a una clase te brinda la habilidad de transformar su estado (es decir sus variables) a una secuencia de bytes. Puedes envolver un FileOutputStream dentro de un ObjectOutputStream y llamar writeObject() para guardar un objeto en almacenamiento, y se puede regresar a memoria desde el archivo con ObjectInputStream y readObject().

en cuanto a lo que es el serialVersionUID es un tipo como de control de versiones para una clase serializada, es para evitar errores de compatibilidad en una misma clase si se guarda al almacenamiento y se modifica la clase, por ejemplo si se le agrega algún método o se le hace algún cambio sustancial. Este UID es pra que la Java virtual machine pueda asegurarse de que la estructura previa y la nueva son compatibles para que no se corrompa nada al intentar reconstruir el objeto
Y la keyword "transient" se le aplica a los atributos para que sean ignorados al serializar, y cuando se reconstruye un objeto desde almacenamiento cualquier campo transient vuelve con su valor por defecto (como null o 0 dependiendo de qué sea), es crucial para cosas como contraseñas y otros datos sensibles porque sin esta característica pueden persistir y es un riesgo de seguridad.
