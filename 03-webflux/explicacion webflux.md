Investigué más sobre Spring WebFlux y ya entendí mejor qué es. Es un framework que surgió como alternativa a Spring MVC. La razón es que MVC/Tomcat está padre pero funciona con un hilo por petición.
Esto significa que al recibir una solicitud HTTP el tomcat le otorga un hilo del pool y es exclusivo. Entonces si esa solicitud que se le hace es algo lento, por ejemplo una consulta a una DB, o algo que requiera esperar, ese hilo se queda bloqueado hasta que obtenga una respuesta o termine el proceso.
Entonces si hay muchos usuarios y el pool tiene una cantidad de hilos que es igual o mayor a la cantidad de hilos, el servidor se cae porque ya no quedan hilos (este fenómeno se llama "thread starvation") y ya no permite conectarse a pesar de que le sobren memoria y/o CPU.
Esa es una gran falla del paradigma imperativo, para apps web que van a tener mucho tráfico pues tener este tipo de desventaja es bastante malo, entonces fue por esto que se desarrolló WebFlux.

WebFlux (que generalmente se usa con el servidor web Netty) se basa en el paradigma reactivo, es dirigido por eventos y trabaja de manera asíncrona; tiene un pool de hilos muy reducido en comparación a Spring MVC y cada vez que un hilo lanza una operación I/O libera el hilo para atender otra petición, y ya que los datos están listos, el mecanismo de eventos avisa para que se retome el procesamiento.
Es bueno para aplicaciones web que vayan a contar con bastante carga de usuarios y este tipo de setup es muy escalable sin tener que invertir mucho en nuevo hardware.

COn WebFlux todo se trata de los Publishers que son los que emiten datos de manera asíncrona. El Mono<T> es un flujo asíncrono que o no emite elementos o emite un solo elemento y luego se completa ya sea exitosamente o no. Por ejemplo en el proyecto, buscar un empleado por su ID con GET /employees/{id} donde o lo retorna o no. 1 elemento o no.
Con el Flux<T> se tiene un flujo asíncrono que emite de 0 a N elementos lo que significa que teoréticamente hasta puede emitir una secuencia infinita. Por ejemplo en el proyecto el listado de todos los registros, o un servicio de streaming de datos de sensores como SensorService que le envía a la interfaz lecturas cada cierto tiempo.

Es muy importante tener en mente cuando uno se adentra a la programación reactiva que en el WebFlux (y también en el Project Reactor que según lo que vi es de donde surgió WebFlux) nada pasa en absoluto hasta que algo o alguien se suscribe, es decir, hasta que se llama el método subscribe(). Esto tiene sentido dada la relación del subscriber y publisher. Básicamente tengo entendido que lo que pasa es que cuando se define un Flux o un Mono se define algo que debe ocurrir de manera declarativa, pero nada pasa hasta que algún cliente HTTP o el propio framework activa la suscripción al flux/flujo.
O sea es más un "ok, cuando alguien llegue y pida esto, haz esto" que un "ok, haz esto" de plano.

También otro concepto importnate que hay que tomar en cuenta es el backpressure, a veces cuando se tiene un flujo de datos rápidos puede pasar que el productor emita más datos de lo que el recipiente ya sea un consumidor o un cliente lo pueda procesar.
Para esto está el backpressure que es un mecanismo con el que cuentan los reactive streams, le da el control al consumidor para solicitr solo la cantidad de lementos que pueda manejar en un momento dado para que no haya errores de falta de memoria.

Uno quizás se pregunte sabiendo todo esto por qué alguien decidiria no usar WebFlux porque suena tan útil y rápido y manejable. Pues hay ciertas situaciones en las aplicaciones donde no conviene, por ejemplo si usas WebFlux pero te conectas a una base de datos con drivers JDBC normales, estos son bloqueantes por naturaleza, así que los hilos se bloquean esperando a la base de datos y pues ya no se tiene la ventaja del WebFlux.
También si se tiene una aplicación que hace cálculos matemáticos muy pesados o algún tipo de cifrado masivo o procesamiento de imágenes o cualquier cosa que sature el CPU, de nada sirve la asincronía porque el CPU estará al cien por ciento y los hilos también se saturarán.
